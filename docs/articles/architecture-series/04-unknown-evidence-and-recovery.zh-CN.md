# 04｜AI 知道自己不知道之后，下一步做什么

传统软件喜欢把条件压成 Boolean：`true` 或 `false`。但现实世界里最危险的一类错误，往往不是“判断错了”，而是**系统其实不知道，却被迫给出了一个确定答案**。

GeoTask 把 Unknown / Unverifiable 当成一等状态，目的不是让系统更保守，而是让“继续前需要补什么”可以被机器表达。

## 1. Unknown 不等于 False

例如，一个任务要求确认某条临时限制是否仍然有效，但当前缺少权威生效时间。如果系统返回 `false`，语义会被理解为“限制不存在”；事实上我们只知道“当前无法验证”。

因此应区分：

```text
CONTRADICTED  = 有证据证明条件不成立
UNVERIFIABLE  = 缺少足够证据，不能判断
CONFLICTED    = 有多个相互冲突且无法按已声明策略消解的证据
```

这三个状态会触发完全不同的下一步。

## 2. Evidence Request 把“不知道”变成可执行计划

当系统发现关键条件不可验证时，最差的行为有两个：

- 继续猜；
- 只输出一句“信息不足”。

更好的行为是生成结构化 Evidence Request，明确：

- 缺失的字段；
- 需要什么类型的来源；
- 哪些输出因此被阻断；
- 在什么条件满足后可以恢复验证；
- 下一步应该向谁或哪个 Provider 请求信息。

于是：

```text
不知道
  ↓
说明为什么不知道
  ↓
请求最小必要证据
  ↓
证据进入
  ↓
重新验证
```

Unknown 从终点变成一个受控恢复状态。

## 3. Conflict 不能靠“最后一个结果覆盖前一个结果”

两个新鲜来源可能同时有效，却给出不同结论。若系统没有显式声明来源优先级、仲裁规则或人工审定机制，就不能自行决定哪个更“权威”。

GeoTask 的原则是：

> 没有声明的来源优先级，不由 Core 发明。

因此 Conflict 的正确行为通常是：

- 保留冲突来源；
- 阻断依赖该事实的关键输出；
- 请求额外证据或显式仲裁；
- 记录恢复条件。

## 4. 新证据进入后，不能只改一个最终答案

补证据成功以后，真正的问题是：哪些状态和判断受到了影响？

Reference Agent 的流程不是“收到新地图位置 → 报告更新”，而是：

```text
新 Observation
    ↓
形成新的 observation-state revision
    ↓
发现旧评估与新现实输入不一致
    ↓
Discrepancy Report
    ↓
Correction Request 限定允许修改的路径
    ↓
Impact Graph 限定需要重算/复核的范围
    ↓
确定性重算
    ↓
后继 World State
    ↓
Control Evaluation
```

这样可以避免一次局部证据变化悄悄触发全局重算，或把无关结论一起“刷新”。

## 5. Fail Closed 不等于永远 Block

Fail Closed 的真正含义是：**当关键前提不成立或无法验证时，不自动升级风险结论或动作权限。**

它同时必须提供恢复路径，否则系统只会变成一个“总是说不”的安全壳。

一个完整的可信循环应同时具备：

- 阻断理由；
- 缺失证据；
- 恢复条件；
- 影响范围；
- 重新验证入口；
- 可重放 Artifact。

## 6. 对 Agent 的意义

未来高风险 Agent 的能力差异，未必首先体现在“回答得更聪明”，而可能体现在：

> 当它不知道时，能否精确知道自己缺什么；当新证据到来时，能否只重算应该重算的部分；当条件仍不闭合时，能否拒绝把 Unknown 包装成确定结论。

这也是 GeoTask 从规则验证走向可信世界状态维护的关键一步。
