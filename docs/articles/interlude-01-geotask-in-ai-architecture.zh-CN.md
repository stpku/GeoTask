# 架构穿插篇01｜GeoTask到底放在AI架构的哪一层？

> 本文属于软件架构穿插线，不占用“GeoTask每周一例”的GT应用编号。
>
> GeoTask不是一个Skill，也不是另一个Agent，而是把任务变成“可计算、可验证、可追溯合同”的中间层。

上一篇文章中，我用一句话定义了GeoTask：

**GeoTask是一种面向AI智能体的可验证时空任务协议，用结构化方式描述空间、时间、证据、资源和行动约束，并通过确定性计算验证模型结论。**

文章发出后，一个很自然的问题随之而来：

GeoTask在今天的AI软件架构中，到底应该放在哪里？

它是一种Skill吗？要不要作为提示词注入Agent？和MCP又是什么关系？

这个问题非常重要。因为如果位置判断错了，GeoTask很容易被理解成又一个工具插件、又一套提示词模板，或者又一个需要单独运行的Agent。

但GeoTask真正要解决的，并不是“让大模型多会一种技能”，而是一个更基础的问题：

**当AI开始规划、调用工具并执行现实任务时，如何把一句自然语言要求，变成机器能够检查、程序能够执行、结果能够复核的任务合同？**

## 一、今天的Agent架构，缺少的往往不是工具

一个典型的Agent工作流程大致是：

```text
用户意图
  ↓
大模型理解与规划
  ↓
调用Skill或MCP工具
  ↓
读取数据、执行程序
  ↓
生成结论或触发行动
```

这套架构已经能够完成很多工作。

问题在于，从“用户意图”到“工具执行”之间，任务通常仍然主要依靠自然语言传递。

例如，用户说：

> 判断一条无人机航线是否与限制区域冲突。

模型可能知道需要检查路线、空域、高度和时间，也可能会调用地图、法规或数据库工具。但在很多系统中，这些条件并没有被明确写成一个可验证对象。

于是就可能出现几种情况：

- 路线相交，模型直接回答“存在冲突”；
- 高度区间并不重叠，但没有被单独检查；
- 限制时间文件尚未核实，模型却根据常识补全；
- 工具返回了数据，但最终结论无法追溯到具体证据；
- 同一个问题换一个模型，执行步骤和判断标准就发生变化。

这并不是模型不会使用工具，而是系统中缺少一个稳定的任务表达层。

GeoTask要补的，正是这一层。

## 二、GeoTask是Agent与工具之间的“任务协议层”

加入GeoTask以后，流程可以变成：

```text
用户意图
  ↓
Agent理解与规划
  ↓
GeoTask结构化任务
  ↓
确定性算子、证据与外部工具
  ↓
结构化验证结果
  ↓
Agent继续决策或执行
```

在这个位置上，GeoTask既不替代大模型，也不替代工具。

大模型仍然负责理解复杂意图、拆解任务和生成方案；地图、数据库、仿真程序仍然负责提供数据与计算能力。

GeoTask负责把中间任务写清楚：

- 任务中有哪些对象；
- 对象使用什么坐标、时间和单位；
- 需要执行哪些算子；
- 哪些结论必须由确定性计算产生；
- 哪些条件已经验证，哪些条件仍然缺证据；
- 什么结果可以继续执行，什么结果必须阻断；
- 补齐什么证据后，任务可以恢复。

因此，更准确地说，GeoTask是一种面向Agent的**任务中间表示**，也是一种**可验证执行协议**。

它把自然语言中的隐含条件，变成显式的机器合同。

## 三、GeoTask不是Skill

Skill通常回答的是：

> 这件事应该怎么做？

例如，一个航线检查Skill可能封装地图查询、几何计算和报告生成流程；一个低空选址Skill可能封装机场距离、人口风险和地面设施评估方法。

GeoTask回答的则是：

> 这一次任务究竟要检查什么，输入是什么，约束是什么，什么结果才算得到验证？

二者的关系更像“合同”和“履约能力”。

Skill提供能力，GeoTask规定本次调用的对象、条件、步骤和验收标准。

同一个Skill可以执行很多不同的GeoTask；同一个GeoTask也可以根据环境选择不同Skill完成。

所以，GeoTask可以被Skill读取，但GeoTask本身不等于Skill。

## 四、GeoTask也不是MCP

MCP解决的核心问题，是让模型或Agent以统一方式连接外部工具、数据和服务。

GeoTask解决的核心问题，是连接之后如何表达和验证具体任务。

可以把二者简单理解为：

- MCP告诉Agent“有哪些数据和工具可以调用”；
- GeoTask告诉系统“这一次应该调用什么、检查什么、如何形成可验证结论”。

例如，MCP可以连接地图服务、法规数据库和气象接口；GeoTask则可以声明：

- 航线是否与区域相交；
- 高度区间是否重叠；
- 限制时间是否已被有效文件证明；
- 三个条件应如何组合；
- 证据不足时最终状态是什么。

因此，GeoTask可以运行在MCP工具之上，也可以在没有MCP的本地程序中独立运行。

它不是连接协议，而是任务协议。

## 五、GeoTask也不应该只是提示词注入

当然，可以把GeoTask规范写进System Prompt，让模型按照固定格式输出YAML。

但如果GeoTask只停留在提示词中，它仍然只是“建议模型这样写”。

真正可靠的系统还需要：

- 对GeoTask文档进行结构校验；
- 对算子名称、输入类型和参数数量进行检查；
- 使用本地确定性程序重新计算关键结论；
- 对模型输出进行标准化和比对；
- 区分已验证、相互矛盾、无法验证和需要人工复核；
- 在证据不足时生成下一步任务，而不是继续猜测。

所以，提示词可以帮助模型生成GeoTask，但GeoTask不能只是一段提示词。

它必须能够离开模型，被独立的程序读取、执行和验证。

## 六、一个最能说明GeoTask位置的例子

假设需要判断一条无人机航线是否与某限制区域构成完整冲突。

经过计算，系统得到：

```text
路线相交：true
高度重叠：true
时间条件：unverifiable
```

传统模型很容易根据前两个条件回答“存在冲突”。

GeoTask则要求三个条件分别给出状态，并且不允许把“时间条件未知”等同于“时间条件成立”。

因此最终结论是：

```text
final_status: unverifiable
next_action: request_evidence
```

系统接下来生成的不是一句含糊的“请进一步核实”，而是一份结构化补证据任务：

```yaml
evidence_request:
  reason: restricted_schedule_not_verified
  required_fields:
    - issuing_authority
    - effective_date
    - start_time
    - end_time
    - document_version
    - source_reference
    - verified_at
  blocked_outputs:
    - full_conflict
    - automatic_approval
  resume_when: restricted_schedule_verified == true
```

这个例子说明，GeoTask不仅帮助AI知道“自己不知道”，还规定知道自己不知道以后应该做什么。

这已经不只是一个计算工具，而是一种任务治理机制。

## 七、GeoTask可以嵌入哪些位置？

在实际系统中，GeoTask至少可以有四种用法。

第一，作为Agent内部的任务中间表示。

Agent完成意图理解后，不直接调用工具，而是先生成GeoTask，再由执行器运行。

第二，作为Skill的输入输出合同。

Skill接收结构化GeoTask，返回带有验证状态、证据来源和执行记录的结果。

第三，作为MCP工具之上的任务编排层。

MCP负责连接地图、法规、气象和数据库，GeoTask负责描述这些工具为什么被调用，以及调用结果如何组成结论。

第四，作为高风险行动前的验证闸门。

只有状态为`verified`的条件才能进入自动执行；`contradicted`、`unverifiable`或`need_review`则进入阻断、补证据或人工复核流程。

## 八、用一句话说清它们的关系

可以这样概括：

**Agent决定做什么，Skill负责怎么做，MCP负责连接什么，GeoTask负责把这次任务变成可计算、可验证、可追溯的合同。**

这也是GeoTask在当前AI软件架构中的主要位置。

它不是为了再造一个Agent，而是为了让现有Agent在处理空间、时间、证据、资源和行动约束时，更少依赖猜测，更多依赖明确的结构、计算和证据。

目前，GeoTask Core已经通过PyPI公开发布。任何人都可以安装：

```bash
pip install geotask-core
```

当前公共版本提供基础任务解析、结构校验、确定性算子、结果标准化与验证能力，并通过一组渐进案例展示从简单距离计算，到多约束冲突、证据缺口和后续行动生成的完整过程。

GeoTask现在还只是一个公共预览版本，但它试图回答的是一个会越来越重要的问题：

**当AI从“回答问题”走向“执行任务”，我们用什么保证它理解的是同一个任务、执行的是明确的条件、给出的是可以复核的结论？**

GeoTask希望成为这个问题的一种基础答案。
