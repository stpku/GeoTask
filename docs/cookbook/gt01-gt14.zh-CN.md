# GeoTask GT01—GT14中文案例手册

[English](gt01-gt14.md) | **简体中文**

这套案例按照“空间关系—时空组合—证据治理—行动与可行性”逐步展开。每个案例只增加一个主要概念，并始终坚持同一原则：

> 模型负责提出候选结论，本地确定性路径负责验证；无法验证时，不强行输出真假结论。

公共体验入口：

```text
https://stpku.github.io/GeoTask/
```

根地址是项目总门户，GT01独立地址为`https://stpku.github.io/GeoTask/gt01/`。Tailscale地址仅作为开发镜像，不是公共Canonical地址。

运行Core案例：

```bash
geotask validate examples/core/<case>.yaml
geotask run examples/core/<case>.yaml
```

## 学习地图

| 阶段 | 案例 | 学习目标 |
|---|---|---|
| 空间关系 | GT01—GT03 | 距离、边界接触和多段路线 |
| 时空组合 | GT04—GT06 | 水平、高度、时间和显式组合规则 |
| 不确定性与证据 | GT07—GT09 | unknown、补证据和证据冲突 |
| 行动与可行性 | GT10—GT14 | 协同动作、对象可达性、能源余量、空间包络和应急调度 |

## GT01：模型报出的距离可信吗？

两个点为`(0,0)`和`(3,4)`，Core通过`distance_2d`得到5米。

```text
模型结果 → 本地distance_2d → verified或contradicted
```

相关文件：

- `examples/core/v1_minimal_distance.yaml`
- `site/gt01/index.html`

核心认识：答案看起来正确，不等于已经经过确定性验证。

## GT02：只碰到边界，算不算相交？

路线只接触限制区边界。当前`line_intersects_rect`契约把边界接触视为相交。

相关文件：

- `examples/route_zone_intersection.yaml`
- `site/gt02/index.html`

核心认识：几何谓词必须明确边界语义，模型不能把“接触”偷偷换成“穿过内部”。

## GT03：最后一段进入限制区，整条路线算相交吗？

一条四点折线的前几段都安全，最后一段进入限制区。

核心认识：路线不等于起点和终点之间的直线；属于路线的每一段都必须参与判断。

相关文件：

- `site/gt03/index.html`

## GT04：水平相交但高度分离，算冲突吗？

两个飞行活动的二维投影重叠，但高度区间分别为`[100,150]`和`[300,500]`。

```yaml
operator: altitude_overlap
```

结果为`false`。核心认识：二维相交不是完整的三维冲突。

## GT05：位置和高度相同，但时间不同，算冲突吗？

活动使用相同空间和高度，但时间分别为`08:00—09:00`和`15:00—17:00`。

```yaml
operator: time_overlap
```

结果为`false`。当前Core采用闭区间语义，端点接触会被视为重叠。

## GT06：多项条件怎样组合？

案例结果：

```text
路线相交 = true
高度重叠 = true
时间重叠 = false
显式AND → 完整冲突 = false
```

相关文件：

- `examples/core/multi_constraint_conflict.yaml`
- `site/gt06/index.html`
- `tests/test_gt06_multi_constraint_case.py`

核心认识：模型不能用自然语言直觉替代任务中写明的组合规则。

## GT07：不知道，不等于没有冲突

路线和高度条件已验证为`true`，但限制时段无法核验。

```text
true AND true AND unknown → unknown / unverifiable
```

相关文件：

- `examples/core/unverifiable_constraint.yaml`
- `site/gt07/index.html`
- `tests/test_gt07_unverifiable_case.py`

核心认识：缺少证据不能被转换成已验证的`false`或`true`。

## GT08：知道自己不知道以后，下一步做什么？

`unverifiable`触发结构化证据请求：

```yaml
evidence_request:
  required_fields:
    - issuing_authority
    - effective_date
    - start_time
    - end_time
    - document_version
    - source_reference
    - verified_at
  blocked_outputs:
    - full_conflict
    - automatic_approval
  resume_when: restricted_schedule_verified == true
  next_action: request_evidence
```

相关文件：

- `examples/core/evidence_request_plan.yaml`
- `site/gt08/index.html`
- `tests/test_gt08_evidence_request_case.py`

核心认识：系统不能只说“请补充信息”，而要生成明确的补证据任务和恢复条件。

## GT09：两份已核验通知互相矛盾，信哪一份？

两份临时禁飞通知分别通过来源核验，却给出不同时间窗。

```text
来源A → temporal_conflict = true
来源B → temporal_conflict = false
跨来源状态 → conflicted
next_action → request_conflict_review
```

相关文件：

- `examples/core/evidence_conflict_review.yaml`
- `site/gt09/index.html`
- `tests/test_gt09_evidence_conflict_case.py`

核心认识：单份证据已核验，不代表多份证据彼此一致；没有权威规则时，模型不能擅自选一份相信。

## GT10：两台机器人抢同一条窄通道，谁先走？

```text
机器人A优先级 = 90
机器人B优先级 = 40
通道容量 = 1
占用时间重叠 = true
```

动作计划：

```yaml
selected_action: robot_b_wait
wait_duration_minutes: 4
revised_entry_time: "08:36"
revised_exit_time: "08:41"
```

相关文件：

- `examples/core/robot_corridor_coordination.yaml`
- `site/gt10/index.html`
- `tests/test_gt10_robot_corridor_case.py`

核心认识：可执行动作需要明确主体、地点、持续时间、新时间窗、政策依据和恢复条件。

## GT11：目标只有50米，机器人为什么绕行300米？

```text
几何距离 = 50米
可通行网络距离 = 300米
绕行系数 = 6
```

轮式机器人不能走台阶、穿围栏或进入机动车道。

```text
accessibility = f(object, network, constraints)
```

相关文件：

- `examples/core/robot_accessible_route.yaml`
- `site/gt11/index.html`
- `tests/test_gt11_robot_accessible_route_case.py`

核心认识：几何上很近，不等于具体对象可以执行。

## GT12：电量够到达，为什么无人机仍不能起飞？

```text
直线距离 = 8公里，但路线违法
合法绕飞 = 11公里
安全余量 = 2公里
总需求 = 13公里
剩余航程 = 12公里
缺口 = 1公里
```

```yaml
selected_action: request_recharge_or_replan
blocked_outputs:
  - launch_clearance
  - automatic_dispatch
resume_when: available_range_km >= total_required_range_km
```

相关文件：

- `examples/core/uav_energy_reserve.yaml`
- `site/gt12/index.html`
- `tests/test_gt12_uav_energy_reserve_case.py`

核心认识：能到达目标和能安全完成任务是两个不同命题。

## GT13：道路开放，车辆为什么还是过不去？

```text
可用通道宽度 = 2.4米
车身宽度 = 2.1米
左侧安全缓冲 = 0.3米
右侧安全缓冲 = 0.3米
所需安全包络 = 2.7米
净空缺口 = 0.3米
```

```text
road_open = true
object_specific_passability = false
```

相关文件：

- `examples/core/vehicle_clearance_envelope.yaml`
- `site/gt13/index.html`
- `tests/test_gt13_vehicle_clearance_case.py`

核心认识：基础设施开放状态与具体对象可通行性必须分别表达，不能为了让候选动作通过而缩小安全缓冲。

## GT14：最近的救援队，为什么不一定最快到达？

```text
A队直线距离 = 2.4公里
A队准备时间 = 4分钟
A队路线时间 = 10分钟
A队预计到达 = 14分钟

B队直线距离 = 5.6公里
B队准备时间 = 1分钟
B队路线时间 = 7分钟
B队预计到达 = 8分钟

响应时限 = 12分钟
```

```text
nearest_team = team_a
fastest_verified_team = team_b
selected_action = dispatch_team_b
```

相关文件：

- `examples/core/emergency_response_fastest_arrival.yaml`
- `site/gt14/index.html`
- `tests/test_gt14_emergency_response_case.py`

核心认识：距离最近只是空间事实，救援调度必须组合可通行路线、准备时间、到达时限和证据时效，验证谁能够最早完成任务。

## 五种可复用模式

### 模式A：确定性命题

```yaml
- id: check
  operator: <registered_operator>
  object_refs: [<object_a>, <object_b>]
```

### 模式B：模型与本地结果比较

```text
模型候选结论
＋
本地确定性结果
→ verified / contradicted
```

### 模式C：缺少证据

```text
unverifiable
→ evidence_request
→ blocked_outputs
→ resume_when
→ 重新计算
```

### 模式D：证据冲突

```text
verified source A ≠ verified source B
→ conflicted
→ conflict review
→ 权威裁决
→ 重新计算
```

### 模式E：可行性门控

```text
显式需求 > 可用能力
→ shortfall
→ blocked action
→ recovery action
→ resume condition
```

## 怎样建设新的GT案例

一个新的公开案例建议包含：

1. 一个具体应用问题；
2. 明确的空间、时间、资源或对象；
3. 能够复用的Core确定性断言；
4. 放在`extensions`中的应用规则；
5. 三个有明显差异的候选动作；
6. 一条本地验证路径；
7. 必要时的安全阻断状态；
8. 明确恢复条件；
9. Core、页面、移动端和导航测试；
10. 真实应用边界说明。

不要为了一个演示方便就新增Core算子。只有具备稳定、通用、可解释契约并有充分测试的语义，才适合进入Core。
