# GeoTask GT01–GT19 Cookbook

This cookbook turns the public weekly examples into a progressive learning path. Each case adds one concept while preserving the same principle: model proposals remain separate from deterministic verification.

Public project portal:

```text
https://stpku.github.io/GeoTask/
```

GT01 starts at `https://stpku.github.io/GeoTask/gt01/`. The Tailscale-hosted address is a development mirror, not the public canonical URL.

Run a Core case:

```bash
geotask validate examples/core/<case>.yaml
geotask run examples/core/<case>.yaml
```

## Learning Map

| Stage | Cases | Question |
|---|---|---|
| Geometry | GT01–GT03 | What spatial relationship is actually true? |
| Space-time composition | GT04–GT06 | Do horizontal, vertical, and temporal conditions all hold? |
| Uncertainty and evidence | GT07–GT09 | What should happen when evidence is missing or conflicting? |
| Action and feasibility | GT10–GT19 | What executable action follows from verified spatial, resource, response, live-environment, multi-UAV conflict, city-event deduplication, equipment-capability, and high-risk action-gate constraints? |

## GT01 — Deterministic Distance

**Question:** Can a model-reported distance be trusted without recomputation?

Core pattern:

```yaml
operator: distance_2d
object_refs: [point_a, point_b]
```

Expected lesson:

```text
model value → local distance_2d → verified or contradicted
```

Relevant files:

- `examples/core/v1_minimal_distance.yaml`
- `site/gt01/index.html`

Use GT01 to learn objects, assertions, local execution, check results, and `local_deterministic` assurance.

## GT02 — Boundary Contact

**Question:** If a route only touches a restricted-zone boundary, does that count as intersection?

Core rule:

```text
boundary contact counts as intersection
```

Relevant files:

- `examples/route_zone_intersection.yaml`
- `site/gt02/index.html`

Lesson: geometric predicates require explicit boundary semantics. A model must not silently substitute “crosses the interior” for the registered `line_intersects_rect` contract.

## GT03 — Multi-Segment Route

**Question:** If early segments are clear but the final segment enters a zone, does the full route intersect?

Relevant files:

- `site/gt03/index.html`

Lesson: a route is not equivalent to the straight line between its endpoints. Every segment that belongs to the route must be considered by the relevant operator.

## GT06 — Explicit Multi-Constraint Composition

**Question:** How should route, altitude, and time conditions be combined?

Case result:

```text
route intersection = true
altitude overlap = true
time overlap = false
explicit AND → full conflict = false
```

Relevant files:

- `examples/core/multi_constraint_conflict.yaml`
- `site/gt06/index.html`

Lesson: a model must not replace an explicit composition rule with an intuitive narrative.

## GT07 — Unknown Is Not False

**Question:** What if route and altitude are verified, but the restricted schedule cannot be verified?

Case result:

```text
true AND true AND unknown → unknown / unverifiable
```

Relevant files:

- `examples/core/unverifiable_constraint.yaml`
- `site/gt07/index.html`
- `tests/test_gt07_unverifiable_case.py`

Lesson: missing evidence cannot be converted into a verified false or true result.

## GT08 — Request Evidence

**Question:** After the system knows that it cannot verify a schedule, what should it do next?

Pattern:

```yaml
evidence_request:
  required_fields:
    - issuing_authority
    - effective_date
    - start_time
    - end_time
    - document_version
    - source_reference
    - verified_at
  blocked_outputs:
    - full_conflict
    - automatic_approval
  resume_when: restricted_schedule_verified == true
  next_action: request_evidence
```

Relevant files:

- `examples/core/evidence_request_plan.yaml`
- `site/gt08/index.html`
- `tests/test_gt08_evidence_request_case.py`

Lesson: `unverifiable` should create a concrete recovery task, not a vague request for “more information.”

## GT09 — Conflicting Verified Evidence

**Question:** Two verified temporary no-fly notices give different time windows. Which one should the model trust?

Case result:

```text
source A: verified → temporal conflict true
source B: verified → temporal conflict false
cross-source state: conflicted
next action: request_conflict_review
```

Relevant files:

- `examples/core/evidence_conflict_review.yaml`
- `site/gt09/index.html`
- `tests/test_gt09_evidence_conflict_case.py`

Lesson: individually verified evidence can still be mutually inconsistent. Without an explicit authority/version rule, the model must not pick a winner.

Action:

selected_action: robot_b_wait

## GT11 — Object-Specific Accessibility

**Question:** The target is only 50 meters away. Why must a delivery robot travel 300 meters?

Case result:

```text
Euclidean distance = 50 m
accessible network distance = 300 m
detour ratio = 6
```

Constraints:

- stairs are not usable by the wheeled robot;
- the fence cannot be crossed;
- the motor-vehicle lane is not permitted.

Relevant files:

- `examples/core/robot_accessible_route.yaml`
- `site/gt11/index.html`
- `tests/test_gt11_robot_accessible_route_case.py`

Lesson:

```text
accessibility = f(object, network, constraints)
```

Geometric proximity is not executable reachability.

## GT12 — Safe Mission Energy Reserve

**Question:** A UAV has enough energy to reach the delivery point. Why is launch still blocked?

Case budget:

```text
direct distance = 8 km, but illegal
legal detour = 11 km
required reserve = 2 km
total requirement = 13 km
available range = 12 km
shortfall = 1 km
```

Action:

```yaml
selected_action: request_recharge_or_replan
blocked_outputs:
  - launch_clearance
  - automatic_dispatch
resume_when: available_range_km >= total_required_range_km
```

Relevant files:

- `examples/core/uav_energy_reserve.yaml`
- `site/gt12/index.html`
- `tests/test_gt12_uav_energy_reserve_case.py`

Lesson: arrival capability and safe completion capability are different propositions.

## GT13 — Vehicle Clearance Envelope

**Question:** The road is open. Why can the autonomous vehicle not pass the work zone?

Case budget:

```text
available passage width = 2.4 m
vehicle body width = 2.1 m
left safety buffer = 0.3 m
right safety buffer = 0.3 m
required envelope = 2.7 m
shortfall = 0.3 m
```

State pair:

```text
road_open = true
object_specific_passability = false
```

Action:

```yaml
selected_action: request_alternate_route_or_controlled_passage
```

Relevant files:

- `examples/core/vehicle_clearance_envelope.yaml`
- `site/gt13/index.html`
- `tests/test_gt13_vehicle_clearance_case.py`

Lesson: infrastructure state and object-specific feasibility must be represented separately. Safety buffers cannot be reduced merely to make a candidate action pass validation.

## GT14 — Fastest Verified Emergency Arrival

**Question:** Why should the farther rescue team be dispatched when it can arrive earlier and meet the response deadline?

Case comparison:

```text
team A straight distance = 2.4 km
team A readiness + route time = 14 min

team B straight distance = 5.6 km
team B readiness + route time = 8 min

response deadline = 12 min
```

Decision:

```text
nearest_team = team_a
fastest_verified_team = team_b
selected_action = dispatch_team_b
```

Relevant files:

- `examples/core/emergency_response_fastest_arrival.yaml`
- `site/gt14/index.html`
- `tests/test_gt14_emergency_response_case.py`

Lesson: proximity is a spatial fact, while emergency dispatch must verify route feasibility, readiness, arrival time, deadline compliance, and evidence freshness.

## GT15 — Static Map, Live Obstacle

**Question:** Why must an inspection robot stop when the map says the corridor is passable?

Case state:

```text
static map corridor_passable = true
map scope = structural_passability
map proves current occupancy = false

live obstacle = temporary pallet
route intersects obstacle = true
safe stop clearance = 4.0 m
minimum stop clearance = 3.0 m
current_passability = false
```

Action:

```text
selected_action = stop_and_replan_route
blocked_outputs = autonomous_forward_motion, continue_without_revalidation
resume_when = obstacle cleared and route reverified
```

Relevant files:

- `examples/core/robot_live_obstacle_stop.yaml`
- `site/gt15/index.html`
- `tests/test_gt15_robot_live_obstacle_case.py`

Lesson: a static map can correctly describe structural connectivity without proving current occupancy. Immediate motion must use evidence that matches the live-state question.

## GT16 — Crossing Routes With Temporal Separation

**Question:** Do two UAVs collide merely because their routes cross and their altitude intervals overlap?

Case state:

```text
route A passes crossing point = true
route B passes crossing point = true
altitude overlap = true
temporal overlap = false

UAV A crossing window = 09:00-09:01
UAV B crossing window = 09:03-09:04
actual separation = 2 min
minimum separation = 1 min
```

Action:

```text
collision_conflict = false
selected_action = maintain_planned_time_separation
required_controls = preserve windows, monitor deviation, recalculate if margin is exceeded
```

Relevant files:

- `examples/core/uav_route_crossing_temporal_separation.yaml`
- `site/gt16/index.html`
- `tests/test_gt16_uav_route_crossing_case.py`

Lesson: route crossing proves shared horizontal location, and altitude overlap adds another necessary condition, but a collision conflict requires overlapping occupancy time at the crossing zone.

## GT17 — Ten Reports, One City Incident

**Question:** Should ten reports of the same incident create ten dispatch tasks?

Case state:

```text
same semantic signature = true
all ten locations within 30 m = true
all ten report windows inside 08:00-08:10 = true

report_count = 10
unique_incident_count = 1
evidence_source_count = 10
```

Action:

```text
selected_action = merge_reports_and_create_one_task
task_count = 1
preserve_source_evidence = true
blocked_outputs = duplicate_dispatch, duplicate_work_orders, source_evidence_loss
```

Relevant files:

- `examples/core/city_event_report_deduplication.yaml`
- `site/gt17/index.html`
- `tests/test_gt17_city_event_deduplication_case.py`

Lesson: a report is evidence, an incident is a real-world entity, and a dispatch task is an action artifact. Deduplication merges the task while preserving every source report.

## GT18 — Shortest Route, Unsafe Robot Entry

**Question:** Why can a rescue robot not use the geometrically shortest route?

Case state:

```text
shortest route = 120 m
shortest route intersects 120°C hazard zone = true
robot maximum operating temperature = 80°C
shortest route executable = false

safe route = 260 m
safe route intersects hazard zone = false
safe route maximum temperature = 60°C
safe route executable = true
```

Action:

```text
selected_action = enter_via_safe_route
blocked_outputs = authorize_shortest_route_entry, ignore_verified_hazard
next_action = dispatch_robot_via_safe_route
```

Relevant files:

- `examples/core/rescue_robot_shortest_route_hazard.yaml`
- `site/gt18/index.html`
- `tests/test_gt18_rescue_robot_route_hazard_case.py`

Lesson: route optimization must satisfy environmental safety and equipment capability before distance or travel time is minimized. Geometric shortest does not mean executable for the current robot.

## GT19 — Arrival Does Not Authorize Payload Release

**Question:** Why can an emergency-supply UAV not release cargo immediately after reaching the target overhead?

Case state:

```text
projection inside drop zone = true
release altitude authorized = true
release time authorized = true
target overhead reached = true

ground responder clearance = 10 m
minimum release clearance = 30 m
ground zone clear = false
immediate release authorized = false
```

Action:

```text
selected_action = hold_position_and_request_ground_clearance
blocked_outputs = payload_release_command, automatic_drop_authorization
resume_when = ground clear and clearance evidence age <= 15 seconds
```

Relevant files:

- `examples/core/uav_arrival_ground_clearance_release.yaml`
- `site/gt19/index.html`
- `tests/test_gt19_uav_ground_clearance_release_case.py`

Lesson: navigation arrival completes only the previous phase. Payload release is a separate high-risk action that needs current ground-clearance evidence, a release-ready payload system, and a recoverable hold-and-reverify workflow.

## Reusable Patterns

### Pattern A — Deterministic proposition

```yaml
- id: check
  operator: <registered_operator>
  object_refs: [<object_a>, <object_b>]
```

### Pattern B — Model/local comparison

```text
model-generated claim
+ local deterministic result
→ verified or contradicted
```

### Pattern C — Missing evidence

```text
unverifiable
→ evidence_request
→ blocked outputs
→ resume condition
→ recompute
```

### Pattern D — Conflicting evidence

```text
verified source A ≠ verified source B
→ conflicted
→ conflict review
→ authoritative resolution
→ recompute
```

### Pattern E — Feasibility gate

```text
explicit requirement > available capability
→ shortfall
→ blocked action
→ recovery action
→ resume condition
```

## Build a New Weekly Case

A new GT case SHOULD include:

1. one concrete application question;
2. explicit spatial/temporal/resource objects;
3. deterministic Core assertions where available;
4. application rules under `extensions`;
5. three differentiated candidate actions;
6. a local verification path;
7. a safe blocked state when necessary;
8. a resume condition;
9. tests for Core behavior, page content, mobile layout, and deployment navigation;
10. a statement of real-world limitations.

Do not add a new Core operator only to make one demonstration convenient. Add an operator when it represents stable, general-purpose semantics with a clear contract and tests.
