# GeoTask GT21–GT28 World-State Cycle Cookbook

This cookbook covers the path from multi-source operational data into a unified state, followed by state change, impact propagation, bounded correction, incremental reevaluation, and action gating. From GT21 onward, every case is scenario-first: the headline states the real task and failure risk, while World State, State Transition, and Artifact terminology is deferred to the technical explanation. Every example uses fictional data and keeps structural validity, exact binding, external truth, and action authorization separate.

## Narrative rule

Each case must answer, in order: what happened in the real task, why it matters, what a generic AI may get wrong, how GeoTask verifies the result, what the user obtains, and what remains unproven. Terms such as Artifact, revision, semantic fingerprint, and materialization must not replace the real-world problem in the headline.

## GT21: Telemetry says 60 seconds, while operations review says 55. Which should the AI use?

The base World State records `uav-b.delay_seconds = 40`. Two fictional Observations then claim 60 and 55 seconds, and the caller maps both claims to:

```text
/objects/uav-b/attributes/delay_seconds
```

Without a target-scoped policy, the merge fails closed with `conflict_policies: duplicates target path without explicit conflict policy`. Core must not apply last-arrival-wins, average unequal values, misuse `require_equal`, or infer which source is authoritative.

The caller supplies a complete `explicit_precedence` order. Core mechanically selects its first application as `applied`, records the other as `superseded`, emits World State revision 2 with a value of 55, and leaves `next_action=compute_state_transition`. This does not establish external truth, source authority, completed impact propagation, output release, or action authorization.

Run the executable case:

```bash
python -m pytest tests/test_gt21_observation_conflict_case.py -q
```

## GT22: Position and battery data come from different systems. How can the AI form one reliable operational snapshot?

Two fictional sensor Observations claim a local ENU position of `(120, 80, 35)` metres and a battery level of 68% for `uav-alpha`. The caller supplies an explicit `object_plan` that names the object, its type, and the target attribute for every claim.

The case-specific builder strictly loads both Observations, requires every claim to be mapped exactly once, fixes the initial snapshot at revision 1, requires `as_of` to equal the latest Observation time, and validates the generated payload through the public World State v0.1 loader and JSON Schema. Reversing the Observation file order produces the same normalized snapshot and semantic fingerprint:

```text
bb57804b830e08dc361bc04e3ca96f4530ea525c198857492dcb6c304dbe540f
```

A reference-closed World State still does not bind the exact source-file bytes. Adding insignificant whitespace to an Observation file leaves its loaded semantics and the World State fingerprint unchanged. Exact byte binding must be established by a later Artifact such as a Verification Session. The snapshot remains `asserted`; it does not establish external truth, compute a State Transition, or authorize action.

```bash
python -m pytest tests/test_gt22_initial_world_state_case.py -q
```

## GT23: Five minutes later, both position and battery have changed. How does the system prove “now” is not “before”?

At 10:02, `uav-alpha` is at local ENU position `(120, 80, 35)` metres with 68% battery. At 10:07, 300 seconds later, the position is `(260, 180, 48)` and the battery is 52%. Overwriting the latest fields would erase the earlier state, the magnitude of change, and the evidence needed to review downstream route-conflict, energy-reserve, or return-to-base decisions.

GT23 retains revision 1, constructs revision 2, and explicitly records three changes:

- position changes from `(120, 80, 35)` to `(260, 180, 48)`;
- battery changes from 68% to 52%;
- the coherent object validity window moves from 10:02:30 to 10:07:30.

The validity refresh is deliberate. The GT22 object expires before 10:07, so a successor snapshot must not silently extend that window.

The case-specific builder strictly loads both new Observations, maps each claim exactly once, constructs the successor World State, and authors a State Transition. It binds revision 1 and revision 2 by world-state ID, `as_of`, and semantic fingerprint, then checks that every declared before/after value equals the corresponding values in the two snapshots.

Successor fingerprint:

```text
4a5112aa71e7286ef37c69ef25af961e15894b25cbe5b7f948dbc4d3b81e1419
```

State Transition fingerprint:

```text
bc12e7c9332e824f27386a43eeae137e493b759fe7dea20b5383539dfaf313e7
```

The public State Transition v0.1 loader validates structure, time order, reference closure, and snapshot bindings, but it does not compute a generic diff or prove that every possible change was discovered. The GT23 builder adds only case-specific validation for the three declared paths. It does not propagate impact, recompute risk, establish external truth, or authorize flight, return, or any other action.
