## GT21：两条观测同时更新同一状态，系统能按到达顺序覆盖吗？

### 场景

基准World State中的`uav-b.delay_seconds`为40秒。随后收到两条虚构Observation：

- 遥测Observation声明延误60秒；
- 运行审核系统Observation声明延误55秒。

两条命题都被调用方显式映射到：

```text
/objects/uav-b/attributes/delay_seconds
```

### 错误做法

- 按文件或消息到达顺序选择最后一条；
- 将60秒与55秒求平均；
- 把不同语义的命题交给`require_equal`；
- 让Core自行判断哪个来源更权威。

这些做法都会引入未声明的排序、推断或数值规则。

### 正确做法

没有目标级冲突策略时，Observation Merge失败关闭：

```text
conflict_policies: duplicates target path without explicit conflict policy
```

调用方随后提供完整策略：

```python
ObservationMergeConflictPolicy(
    target_path="/objects/uav-b/attributes/delay_seconds",
    strategy="explicit_precedence",
    precedence=(
        "obs-uav-b-delay-ops-review#uav-b-delay-seconds",
        "obs-uav-b-delay-002#uav-b-delay-seconds",
    ),
)
```

Core只机械执行这份完整顺序：

- 审核记录application：`applied`；
- 遥测application：`superseded`；
- 后继World State：revision 2；
- `delay_seconds`：55秒；
- `next_action`：`compute_state_transition`。

### 安全边界

该结果不证明审核记录真实、权威或经过独立核验，也不代表State Transition已经计算、影响已经传播、输出已经释放或行动已经授权。真实优先级规则必须由调用方、Runtime或Domain Pack明确提供。

```bash

```

## GT22：两条Observation如何构建第一个可引用World State？

### 场景

两条虚构传感器Observation分别声明：

- `uav-alpha`在本地ENU坐标系中的位置为`(120, 80, 35)`米；
- `uav-alpha`电量为68%。

Observation只表达带来源、时间和不确定性的命题。调用方必须另外提供显式`object_plan`，声明对象ID、对象类型以及每个claim进入哪个属性。

### 构造门禁

GT22案例构造器要求：

- 每个Observation先通过严格加载；
- 首个快照固定为revision 1；
- `as_of`等于最新Observation时间；
- 每个claim恰好映射一次；
- claim的`subject_ref`必须等于调用方声明的对象ID；
- 不支持未声明对象、重复属性或关系claim；
- 生成结果再次通过World State v0.1严格加载和JSON Schema验证。

固定结果包含一个`uav-alpha`对象、两个属性、两条Observation引用和两条Evidence引用，语义指纹为：

```text
bb57804b830e08dc361bc04e3ca96f4530ea525c198857492dcb6c304dbe540f
```

### 关键边界

World State的引用闭包不等于Observation原始文件字节绑定。只改变Observation JSON的空白字符，严格加载后的语义和World State指纹仍可保持不变。精确文件绑定需要由Verification Session等后续制品明确完成。

该快照的可信状态仍为`asserted`；它不证明外部真实，不计算State Transition，也不授权行动。

```bash
python -m pytest tests/test_gt22_initial_world_state_case.py -q
```

构造示例：`examples/core/gt22_build_initial_world_state.py`。

体验页面：`site/gt22/index.html`。
