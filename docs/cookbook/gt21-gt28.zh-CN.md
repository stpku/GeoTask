# GeoTask GT21—GT28 世界状态循环案例手册

本手册覆盖GeoTask从多源运行数据进入统一状态，到状态变化、影响传播、限定纠偏、增量复核和行动门控的案例。GT21之后统一采用“现实场景优先、必要性先行、技术概念后置”的叙事：主标题先说明用户正在处理的任务和可能犯的错误，World State、State Transition等术语只在技术实现部分解释。每个案例都使用虚构数据，并区分结构有效、精确绑定、外部真实和行动授权。

## 案例叙事规则

每个案例页面必须依次回答：现实中发生了什么、为什么必须解决、普通AI容易犯什么错误、GeoTask如何验证、用户最终得到什么，以及仍然不能证明什么。Artifact、revision、semantic fingerprint、materialization等术语不得替代现实问题成为主标题。

## GT21：遥测显示延误60秒，运行审核记录显示55秒，AI应该相信哪一个？

### 场景

基准World State中的`uav-b.delay_seconds`为40秒。随后收到两条虚构Observation：

- 遥测Observation声明延误60秒；
- 运行审核系统Observation声明延误55秒。

两条命题都被调用方显式映射到：

```text
/objects/uav-b/attributes/delay_seconds
```

### 错误做法

- 按文件或消息到达顺序选择最后一条；
- 将60秒与55秒求平均；
- 把不同语义的命题交给`require_equal`；
- 让Core自行判断哪个来源更权威。

这些做法都会引入未声明的排序、推断或数值规则。

### 正确做法

没有目标级冲突策略时，Observation Merge失败关闭：

```text
conflict_policies: duplicates target path without explicit conflict policy
```

调用方随后提供完整策略：

```python
ObservationMergeConflictPolicy(
    target_path="/objects/uav-b/attributes/delay_seconds",
    strategy="explicit_precedence",
    precedence=(
        "obs-uav-b-delay-ops-review#uav-b-delay-seconds",
        "obs-uav-b-delay-002#uav-b-delay-seconds",
    ),
)
```

Core只机械执行这份完整顺序：

- 审核记录application：`applied`；
- 遥测application：`superseded`；
- 后继World State：revision 2；
- `delay_seconds`：55秒；
- `next_action`：`compute_state_transition`。

### 安全边界

该结果不证明审核记录真实、权威或经过独立核验，也不代表State Transition已经计算、影响已经传播、输出已经释放或行动已经授权。真实优先级规则必须由调用方、Runtime或Domain Pack明确提供。

### 运行测试

```bash

```

## GT22：无人机的位置和电量来自两个系统，AI怎样形成同一时刻的可靠运行快照？

### 场景

两条虚构传感器Observation分别声明：

- `uav-alpha`在本地ENU坐标系中的位置为`(120, 80, 35)`米；
- `uav-alpha`电量为68%。

Observation只表达带来源、时间和不确定性的命题。调用方必须另外提供显式`object_plan`，声明对象ID、对象类型以及每个claim进入哪个属性。

### 构造门禁

GT22案例构造器要求：

- 每个Observation先通过严格加载；
- 首个快照固定为revision 1；
- `as_of`等于最新Observation时间；
- 每个claim恰好映射一次；
- claim的`subject_ref`必须等于调用方声明的对象ID；
- 不支持未声明对象、重复属性或关系claim；
- 生成结果再次通过World State v0.1严格加载和JSON Schema验证。

固定结果包含一个`uav-alpha`对象、两个属性、两条Observation引用和两条Evidence引用，语义指纹为：

```text
bb57804b830e08dc361bc04e3ca96f4530ea525c198857492dcb6c304dbe540f
```

### 关键边界

World State的引用闭包不等于Observation原始文件字节绑定。只改变Observation JSON的空白字符，严格加载后的语义和World State指纹仍可保持不变。精确文件绑定需要由Verification Session等后续制品明确完成。

该快照的可信状态仍为`asserted`；它不证明外部真实，不计算State Transition，也不授权行动。

## GT23：无人机飞行五分钟后位置和电量都变了，系统如何证明“现在”不是“刚才”？

### 场景与必要性

10:02时，`uav-alpha`位于本地ENU坐标`(120, 80, 35)`米，电量68%；300秒后的10:07，位置变为`(260, 180, 48)`米，电量降至52%。如果系统只覆盖最新字段，历史状态、变化幅度和变化依据都会丢失，后续航线冲突、电量余度和返航判断也无法复核。

GT23保留revision 1，构建revision 2，并明确记录：

- 位置从`(120, 80, 35)`变为`(260, 180, 48)`；
- 电量从68%变为52%；
- 对象有效期从10:02:30刷新至10:07:30。

有效期刷新是必要的：GT22对象原有效期早于10:07，不能为了生成后继快照而静默延长。

### 构造与绑定

案例构造器严格加载两条新Observation，要求每个claim恰好映射一次，并生成后继World State。随后构造State Transition，绑定同一`world_state_id`下的revision 1与revision 2、各自`as_of`和语义指纹，并逐项检查声明的before/after值确实等于两个快照中的值。

固定后继快照指纹：

```text
4a5112aa71e7286ef37c69ef25af961e15894b25cbe5b7f948dbc4d3b81e1419
```

固定State Transition指纹：

```text
bc12e7c9332e824f27386a43eeae137e493b759fe7dea20b5383539dfaf313e7
```

### 关键边界

公共State Transition v0.1加载器验证结构、时间顺序、引用闭包和快照指纹绑定，但本身不执行通用diff，也不证明所有变化已经自动发现。GT23构造器仅对本案例显式声明的3条路径执行额外核验。

该结果不传播影响，不重算风险，不验证外部真实，也不授权飞行、返航或其他行动。下一步是评估哪些任务和结论受到变化影响。

### 运行测试

## GT24：临时禁飞区发布后，哪些航线、任务和审批结论必须重新检查？

### 场景与必要性

一处虚构临时禁飞区在14:00—16:00生效。医疗航线A计划于14:30—14:50飞行，调用方声明其与禁飞区相交；巡检航线B计划于14:35—14:55飞行，调用方声明其从区域南侧绕开。

系统不能采用两个极端做法：

- 不能把所有航线、任务和审批全部重算，否则会无依据扩大业务影响；
- 不能只更新地图后继续沿用旧任务放行和审批结论，否则下游决策会与当前空域状态脱节。

GT24将影响范围限定为：

- 医疗航线A的空域避让断言；
- 医疗任务17的放行断言和调度输出；
- 医疗审批17的放行结论；
- 医疗任务17的起飞动作。

巡检航线B、巡检任务08及其审批不进入该影响图。

案例将虚构禁飞通知加载为Observation，将当前航线、任务和审批清单加载为World State revision 2，再生成一份Discrepancy Report，记录旧医疗任务放行结论已经过时。Impact Graph以该差异为根，连接7个节点、7条边和4个复核目标，阻断2个输出和1个起飞动作。

## GT25：无人机位置更新后，哪些安全距离需要重算，哪些结果可以继续沿用？

### 场景与必要性

无人机沿一条虚构直线巡检走廊从里程100米移动到130米。起重机位于150米，通信塔位于260米。旧状态仍保存无人机—起重机50米、无人机—通信塔160米两项距离；固定设施间距110米和电池余量48%仍在各自有效期内。

系统不能采用两个极端做法：

- 不能因为位置变化就把全部结果作废，否则会无依据推翻固定设施间距和电池数据；
- 不能只改位置或只重算最近的起重机距离，否则通信塔距离仍会使用旧位置结果。

GT25将重算范围限定为两条路径：

```text

/relations/uav-alpha-tower-distance/value
```

```text

/objects/uav-alpha/attributes/battery_percent/value
```

- 起重机位置150减去无人机位置130，结果20米；
- 通信塔位置260减去无人机位置130，结果130米。

## GT26：飞行服务站营业时间已经失效，系统应该改哪条数据，而不是推翻全部结果？

### 场景与必要性

当前World State仍记录虚构飞行服务站每日08:00—22:00开放。新公告将营业时间调整为09:00—18:00，并于2026年8月4日18:00生效。任务27计划在20:30请求服务，旧状态仍将其标记为可服务。

系统不能采用两个极端做法：

- 不能因为营业时间失效就删除整条站点记录，否则位置编码、通信频率、服务类型和联系方式也会被无依据丢弃；
- 不能只替换营业时间后立即继续派发，因为20:30任务的旧可服务结论尚未重新检查。

GT26只允许修改一条路径：

```text
/objects/flight-service-station-east/attributes/operating_schedule/value
```

并明确保留四条不可变路径：位置编码、通信频率、服务类型和联系方式。

### 差异与纠偏

Discrepancy Report把旧计划08:00—22:00记录为`observed`，把公告计划09:00—18:00记录为`expected`，并将任务27可服务结论、任务输出和派发动作列入影响范围。

Correction Request仅包含一个`replace`操作，要求：

- `before`必须等于当前状态中的旧计划；
- `after`必须精确等于公告Observation中的新计划；
- 后继World State至少为revision 5；
- 四条不可变路径必须保持不变；
- `mission_27_service_availability`和`dispatch_mission_27`继续阻断；
- 只有后继状态有效且20:30任务完成复核后才可恢复。

固定World State指纹：

```text
d1d73bd3ee443a0f506311a4d68f85ab713d60674e9cc98d630584f49edaa26c
```

固定Discrepancy Report指纹：

```text
bcbc6d5644c9bcbde03163dc9024f9c5a9d0e9dc0c3cdcd8df8ba2bff0f91b83
```

固定Correction Request指纹：

```text
aa165ba2e6ee673008c8bcbaeab719c4d99ce19ab5a103f1f7ef5303b700b259
```

### 失败关闭与边界

扩大可改范围、让可改路径与不可变路径重叠、将公告结束时间改为其他值、缺少任务复核验收条件或篡改公告文件字节，案例都会失败关闭。

公共Core验证的是调用方声明的差异和纠偏范围，不主动获取或比较真实公告。该结果不应用修订、不生成后继状态、不执行任务复核、不发布输出、不验证外部真实，也不授权或执行派发动作。

## GT27：一条气象数据更新后，如何只复核受影响的飞行任务？

### 场景与必要性

东区14:00风速由原运行假设6米/秒更新为12米/秒。系统中有四项任务：东区14:30配送任务风速上限10米/秒，西区14:30巡检任务上限10米/秒，东区12:30测绘任务上限10米/秒，东区14:45应急任务上限15米/秒。

revision 7已经吸收12米/秒的新Observation，但四项任务仍保留旧的适飞结果。系统不能把四项任务全部重算，也不能只复核最终会变成`false`的任务：任务D虽然复核后仍为`true`，也必须留下使用新气象值重新检查的证据。

### 增量复核结果

调用方声明的区域—时段依赖范围只包含任务A和任务D：

- 任务A：`12 <= 10`，由`true`变为`false`；
- 任务D：`12 <= 15`，由`true`保持`true`，但完成了显式复核；
- 任务B：区域不同，结果继续复用；
- 任务C：计划时刻早于更新生效时间，结果继续复用。

## GT28：路线安全、天气合格，就可以自动起飞吗？

### 场景与必要性

一架虚构无人机计划于14:20起飞。路线不穿越限制区，计划高度与允许高度区间重叠，天气预报窗口覆盖起飞时段，风速8米/秒低于12米/秒上限。技术预检全部通过，但授权登记中仍缺少空域、运营人、起降场、气象放行和任务授权五项独立信息。

系统不能把“安全条件满足”直接提升为“行动已经授权”，也不能根据路线安全和天气良好推断缺失授权已经存在。

### 输出门禁与行动资格

固定执行结果验证三项条件：

- `route_intersects_restricted_zone = false`；
- `altitude_within_operating_corridor = true`；
- `weather_window_valid = true`；
- 显式状态满足`8 <= 12`。

Control Evaluation识别五个`unknown_identifiers`，保持以下输出阻断：

```text
automatic_takeoff_authorization
takeoff_command
```

Verification Session同时记录：

```text
route_weather_precheck        eligible
automatic_takeoff_authorization blocked
takeoff_command                blocked
```

这证明“可引用的预检结论”和“可执行的起飞动作”属于不同层级。

固定World State指纹：

```text
e7f181dae9be455fba6ffcbeba84271214778efb6052f13094782ffb95ad3c2b
```

固定Control Evaluation文件SHA-256：

```text
7377d9e3f1db7b16aa4c806f90c64efd27107815f394bf3792b7a29ee8ebd0e1
```

固定Verification Session指纹：

```text
cc955b90955a5f90c20464500aacdc093b528aa402e9e9b1c9c337bb2e41df75
```

### 关键边界

即使未来五项授权全部显式变为`true`，公共Control Evaluation也只会把两个输出标记为`eligible`，其`action_executed`仍固定为`false`。公共Core不联系真实主管部门，不验证外部授权真实性，不发布生产输出，不发送起飞指令，也不执行飞行动作。

下一步只能是补齐授权包并重新验证，而不是从安全条件推断授权。
